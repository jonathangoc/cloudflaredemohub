# 05: Secure A2A

## Purpose

Connect the public Seven Hills shopping agent to a private product-support agent using the Agent2Agent (A2A) protocol. You will bring the support VM onto Cloudflare Mesh, connect the existing Worker with a VPC Network binding, authenticate the workload with Access, and observe the delegated task in Gateway.

**Target time:** 18 minutes. Confirm the complete timing during the lab pilot.

:::info One customer experience, two agents
Sofia remains the customer-facing shopping assistant. When a customer explicitly requests specialist product support, a deterministic application router delegates the request to the private Support Agent. The Support Agent has diagnostic skills and knowledge that Sofia does not have.
:::

## Architecture Context

```text
Website user
    |
    | Specialist-support request
    v
Seven Hills Worker (A2A client)
    |
    | A2A 1.0 JSON-RPC + Access service-token headers
    v
Workers VPC Network binding: SUPPORT_NETWORK
    |
    v
Cloudflare Gateway ---------> HTTP request logs and policy
    |
    v
Cloudflare Access ----------> Service Auth: seven-hills-agent
    |
    v
Cloudflare Mesh
    |
    v
Support Agent on pod VM ----> Private diagnostic skills
```

The Worker calls the VM's Mesh IP over Cloudflare One rather than exposing the Support Agent to the public Internet. Gateway evaluates and records the private HTTP exchange. Access then checks the Worker's machine identity before the request reaches the VM.

### Why this matters

A2A standardizes collaboration between independent agents. It does not make every discovered agent trustworthy or authorize every caller. This module applies separate controls to four questions:

1. How does the customer-facing agent privately reach the remote agent?
2. Which workload is allowed to invoke it?
3. Which requests are inspected and recorded?
4. Which customer requests should be delegated?

### A2A is not MCP

| Protocol | Relationship | Seven Hills example |
| --- | --- | --- |
| MCP | An agent invokes a narrow tool or resource. | Sofia retrieves inventory from an Operations tool. |
| A2A | One agent delegates a goal to another agent that manages its own reasoning, skills, and task lifecycle. | Sofia delegates a Bluetooth problem to the Support Agent. |

The Support Agent remains opaque. Seven Hills sees its Agent Card, messages, task state, and artifacts, but not its private prompt, memory, or tools.

:::warning Publication gate
The current application baseline does not yet implement the A2A client, fixed support router, safe diagnostic endpoints, or support attribution described by this module. Before publication, verify the complete flow in a lab account, including that a request from a Workers VPC Network binding is evaluated by the private Access application on port `8080`, the Worker dashboard binding workflow, and Gateway HTTP policy and log fields.
:::

:::caution Keep machine credentials server-side
The browser must never receive the Access Client ID or Client Secret. The Worker adds them only to server-side requests made through `SUPPORT_NETWORK`.
:::

## Expected Result

The customer asks for specialist help with Aurora Buds Pro after a firmware update. Seven Hills delegates the issue through A2A, displays the Support Agent's diagnostic artifact with its task ID, and leaves ordinary shopping questions on Sofia's local path. The Support Agent remains private, rejects an unauthenticated workload, and produces a matching allowed event in Gateway.

## What You Built

| Layer | Control | Outcome |
| --- | --- | --- |
| Application | Deterministic support router | Only the approved lab support intent enters the A2A path. |
| A2A | Agent Card and `SendMessage` | Seven Hills discovers a specialist capability and delegates a task. |
| Workers VPC | `SUPPORT_NETWORK` | The Worker reaches the VM by private Mesh IP. |
| Mesh | Pod VM node | The private Support Agent joins Cloudflare One without a public hostname. |
| Access | Service Auth | Only the approved workload identity may invoke the private application. |
| Gateway | HTTP policy and logs | The inter-agent exchange is governed and auditable. |

## Production Caveats

- Workers VPC and VPC Network bindings are beta services. Revalidate availability, limits, roles, and configuration before production use.
- A2A 1.0 supports JSON-RPC, HTTP+JSON, and gRPC bindings. Pin and test the interface and protocol version advertised by the Agent Card.
- The lab uses plaintext HTTP inside the encrypted Mesh path for simple Gateway inspection. A2A recommends HTTPS in production; use trusted certificates and verify server identity.
- An Access service token identifies the Seven Hills workload, not the customer. The Support Agent must separately authorize customer data and high-impact actions.
- Reusing one workload identity keeps the lab short. Use separate credentials when agents have different privileges, owners, or rotation schedules.
- Do not rely on a system prompt to route security-sensitive requests. Production routing should combine deterministic policy, constrained classification, authorization, and safe fallback behavior.
- Send only the context required by the specialist. Do not forward the entire conversation, cart, or customer profile by default.
- Gateway logs can reveal destinations, paths, and request metadata. Configure retention and payload collection according to privacy requirements.
- Gateway inspects HTTP on port `80` by default. This lab requires **Inspect on all ports** because the Support Agent uses port `8080`.
- Agent Cards can expose sensitive capabilities and internal endpoints. Protect private cards and consider authenticated extended cards or signed Agent Cards where appropriate.
- High-impact skills such as refunds, replacements, or account changes require skill-level authorization and confirmation beyond network access.
